# 第一部分：题眼（用户提出，我认为是对的）

> Dynamic Dispatch 都能发车，为什么按表排不出来？尤其是有 wait 和非固定 frequency 的情况。

同一张网、同一批 route，运行时的调度器跑得动（车在资源前排队、等、然后走），编表却在 300 秒间隔上给出
1909 处冲突并构建失败。**两边在解不同的问题，而编表这一边被限制得严得多。**

把两边的自由度摆在一起：

| | 运行时（Dynamic Dispatch） | 编表（build） |
| --- | --- | --- |
| 发车时刻 | headway 触发，资源可用才走 | 钉在网格上（`slot × 间隔 + 相位`） |
| 等待 | **无界、自适应**，任何资源前都能等 | **单处 ≤ `--max-wait` 60 s**（封顶 `hold-max-seconds` 120 s） |
| 等待的上限依据 | `queued-ticket-max-age-seconds = 7200` | 60 / 120 |
| 交会点 | 由实际运行决定，每次可以不同 | 由相位余数**固定**，每个周期都在同一处 |
| 需要的全局性质 | 无。每一步局部可行 + 不死锁即可 | **全表同时无冲突** |
| 失败的样子 | 晚点 | 构建失败，一班都发不出 |

**等待预算差 60–120 倍**（7200 vs 60）。这一条我认为是主因之一：编表把"现实中车会等一下"这件事的预算
设成了运行时实际容忍度的百分之一，于是把大量现实可行的表判成了不可行。

`docs/dev/timetable-departure-design.md` §10 里已经挂着这条：

> **冲突预算**：允许表里保留某类残余冲突（例如咽喉上 ≤ N 处）交给运行时让车，而不是一律放宽 headway。
> 用户的直觉（"让列车在一些情况下 wait，这是 Dynamic Dispatcher 的事"）指向这里；本轮不做，
> 因为需要先定义"哪类冲突运行时一定能让、代价可控"。

**这一轮就是要做那件被推迟的事**，而且现在有实测数据了。

# 第二部分：实测（对实服库副本跑当前算法，不是推测）

探针：`.handoff/LiveNetworkProbeTest.java.txt`（复制到 `src/test/.../timetable/` 即可跑，DB 用实服库**副本**，
永远别直接打开实服库；用完删掉不提交）。口径：窗口 05:00–24:00，`--dwell 20`，折返按终到站 dwell，
**套了 445 条永久限速覆盖**，`strict=true`（每个间隔只跑一次 attempt，不进搜索）。

## 2.1 WS：420 秒可行，300 秒 1909 处冲突

| 目标 | 结果 | 冲突分布 |
| --- | --- | --- |
| 1200 s | ✅ 0 | — |
| 900 s | ✅ 0（让车 152 处） | — |
| 600 s | ✅ 0 | — |
| 420 s | ✅ 0（让车 12 处） | — |
| **300 s** | ❌ **1909** | 区间 863 / 单线对向 453 / 道岔 593 |
| 240 s | ❌ 787 | 站台 4 / 单线 207 / 区间 299 / 道岔 277 |
| 180 s | ❌ 2374 | 区间 1041 / 单线 749 / 道岔 584 |
| 120 s | ❌ 6006 | 站台 835 / 区间 2594 / 道岔 1327 / 单线 1250 |

## 2.2 MT：**任何间隔都排不出来，1200 秒也不行**

| 目标 | 冲突 |
| --- | --- |
| **1200 s** | **209**（站台 45 / 区间 117 / 道岔 40 / 单线 7） |
| 900 s | 302 |
| 600 s | **7903** |
| 420 s | 901 |
| 300 s | 1392 |
| 240 s | 4585 |
| 180 s | 15226 |

一条 6 route 的线在 20 分钟间隔下排不出来，物理上不可能。**600 s 比 420 s 差 9 倍**，也不是容量能解释的。

## 2.3 冲突与车流量**无关**（这条最关键）

同样 300 s，把别的线的带客走行 route 排除掉：

```
保留：1292 班 / 486 交路 → 1899 处冲突
排除： 644 班 / 162 交路 → 1909 处冲突
```

**班次砍一半、交路砍三分之二，冲突数纹丝不动。** 所以不是拥挤，是几何。

## 2.4 根因之一已坐实：相位共振

直接算时分（不 build）：

```
WS-2C_FullR  OPERATION  走行 575  折返 30   → (575+30) mod 300 = 5     mod 420 = 185
WS-2N_FullR  OPERATION  走行 582  折返 20   → (582+20) mod 300 = 2     mod 420 = 182
```

`PhasePlanner.anchorReturnPairs` 的规则是 **反向相位 =（正向走行 + 折返）mod 间隔**，注释写明目标是
"一辆车到端点折返完正好是下一班的时隙，**端点零等待**"。

但当往返走行时分接近间隔的整数倍时，"端点零等待"与"**两个方向同时发车**"是同一件事。两列对向车同时从两端
出发，必然在线路中点附近交会，交会点由相位**固定**，每个周期都在同一处。落在单线区段上就每对必撞。

- 300 s：余数 5 / 2 → 同相 → 1909 处
- 420 s：余数 185 / 182 → 接近半周期，错得最开 → 0 处

三个现象（悬崖、非单调、与流量无关）一次解释完。

**相位规划现在只有两层，两层都只看端点**：往返对锚定（端点零等待）、组间在共用起点上错开。
**没有任何一层看沿线交会点**——而那正是现实单线铁路编图的核心工作（会让点要落在有避让线的地方）。

## 2.5 MT 的失败另有成因，未查明

2.4 解释不了 MT 在 1200 s 就崩：那一档没有任何 route 的相位余数接近 0。MT 有两个交路组
（`MT-1_Short` baseline 150、`MT-2_Fueya` 120），可能是组间交互，也可能是下面 2.6 的污染，也可能是别的。
**这是你要查的第一件事。**

## 2.6 一个独立的 bug（不需要设计，但会污染你的测量）

编表时 CREATE/RETURN 的搜索范围是**本 operator 全部线路**（为了找出库/回库途径），而 Q1 规定
"中途有 STOP 的 CREATE/RETURN 是**带客 route**，它是班次，上子网格"。两条规则一叠：

- 给 WS 编表时，`DS-1F_Full`（CREATE，属 DS 线）与 `MT-2F_Short`（CREATE，属 MT 线）被当成**班次**排进了 WS 的表
- `Timetable.managedRouteIds()` 只过滤 `external`（跨 operator 的显式引用），同 operator 不同线的**不算** external
- 于是 WS 的表一发布，会把 DS 和 MT 自己的 headway 票也拦掉；若再给 DS 单独编表，同一条 route 会出现在两张
  已发布的表里，两边都发票

（顺带：DS 探索线**没有 OPERATION route**，整条线就是一对 CREATE + RETURN，这是 Q1 明确支持的写法，
所以它特别容易被别的线"吸"进去。）

## 2.7 性能（本轮不是题目，但你会撞上）

jstack 抓到热点：`ResourceRepair.repair → scan → TimetableConflictChecker.check → project → resource`
（`HashMap.computeIfAbsent`，字符串键）。**每施加一处让车就把整张表重新投影一遍**，
循环上界 `cap = 4 × trips + 8`。实测：稀疏档 30–700 ms，`WS@300s` 单次 attempt **127 秒**，`WS@120s` **1065 秒**。
再叠上搜索（候选数 = 0.3 × 目标间隔）就是小时级。你的方案如果增加扫描次数，要说明怎么不让它更糟。

# 第三部分：先做这件事（在设计之前）

不要直接开始设计。三步，结论写进交接文档最前面：

1. **查 MT 为什么在 1200 s 就失败。** 先排除 2.6 的污染（只留纯走行 route 重跑），再看剩下的 209 处冲突
   落在哪些资源、哪些 route 对之间。这是本轮最大的未知。
2. **验证等待预算这条主因。** 把 `--max-wait` 从 60 提到 300、600、1800（先解开 `hold-max-seconds` 的封顶），
   重跑 `WS@300s` 与 `MT@1200s`。**如果冲突数大幅下降甚至归零，"编表的让车预算比运行时小两个数量级"就是主因**，
   本轮的题目就清楚了。如果不降，说明让车机制本身有结构性限制（"只延后"、回滚判据、沿交路链传播），
   那要说明是哪一条挡住了。
3. **验证相位共振。** 对 WS 扫 290–430 秒（10 秒步长），画出冲突数与 `(走行+折返) mod 间隔` 的关系。
   如果冲突谷底正好落在余数接近半周期的地方，2.4 成立。

三步都能用探针脚本做。**推翻我的任何一条都直接说，不要顺着我的话往下设计。**

# 必须保住的不变量

1. 时刻表是从路网**算**出来的，不是**录**出来的。
2. 同一份网络状态 + 同一份配置 + 同一组已发布邻表，永远产出同一张表，包括 trip/duty 主键。
3. weight 是目标服务比例（SWRR），不是抽签概率。
4. 每辆实体车都有有限交路且最终必须回库，终止性能在构建产物上直接断言。
5. 先定班次、再派车，顺序不可交换。
6. 宁可少排一班，也不排一班发不出去或回不了库的车。
7. 冲突模型只做纯数据运算、不跑调度器；回放只用于校验，永远不作为 build 输入。

**其中 6 最可能被本轮挤压**——"允许残余冲突"与"宁可少排一班"是同一个尺度上的两端。
挤压可以，但必须给出进 `docs/dev/timetable.md` 的**确切新措辞**，并说明新说法为什么仍然可检验。
